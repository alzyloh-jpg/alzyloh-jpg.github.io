Imitation learning: how the Nero arms learn

In this project, an expert means the person demonstrating the task. The human demonstrates placing Tic Tac Toe pieces using VR controllers or a master arm. The robot records camera images and joint positions as observations (state, s) together with the operator's movements (action, a). These pairs form a demonstration dataset.

1. Demonstration data

The dataset can be written as:

D = {(s₁, a₁), (s₂, a₂), …, (sN, aN)}

  • s is the state or observation.
  • a is the action taken by the expert.
  • D is the dataset of demonstrations.

2. Behaviour cloning

Behaviour cloning learns policy parameters θ that make the policy output close to the expert's action across the demonstration examples:

minθ E(s,a) ∈ D[ℓ(πθ(s), a)]

Here, πθ(s) is a policy—often a neural network—that takes a state and outputs an action. The loss ℓ measures the difference; for continuous actions it is commonly squared error (L2) or absolute error (L1). A probabilistic formulation maximizes the sum of log πθ(a | s), making the demonstrated action likely under the policy.

3. DAgger (Dataset Aggregation)

  1. Run the current policy πi and collect states from the situations it actually encounters.
  2. Ask the expert for the correct action a* = πexpert(s) for those states.
  3. Add those state-action pairs to the dataset: D ← D ∪ {(s, a*)}.
  4. Retrain on the combined dataset to obtain πi+1.

Because training includes states visited by the learner, along with expert corrections, this approach addresses the mismatch between demonstration states and the states the learned policy may encounter. The supplied notes describe error growth as roughly ε · T.

4. GAIL

Generative Adversarial Imitation Learning (GAIL) trains a policy against a discriminator D that tries to distinguish policy behaviour from expert behaviour:

minπ maxD Eπ[log D(s, a)] + Eexpert[log(1 − D(s, a))]

The discriminator learns to spot policy-generated behaviour, while the policy learns to make its behaviour resemble the expert's.

Connection to this project

We aim to teach a Nero arm to place Tic Tac Toe pieces by imitation learning. Human demonstrations, recorded camera observations, joint positions, and operator actions form the dataset used to train an ACT model, a form of behaviour cloning. Imitation learning can be affected when a policy drifts into states not represented in its demonstrations. ACT addresses part of this challenge by predicting a chunk of future actions at once.

YOLO Tic Tac Toe vision system: project overview

What we are building

The planned system uses an overhead webcam and a custom YOLO11n model to observe a real 3 × 3 Tic Tac Toe board. It detects two piece classes, called object_A and object_B, maps each piece to a square, reduces visual flicker, and displays a live camera view beside a digital board.

Design goals

  • Runs on Windows 11 and Linux: use the same project code on both platforms.
  • Modular: keep camera, detection, grid mapping, and display tasks in separate files so they can be tested independently.
  • Configurable: keep camera indices, board corners, and detection thresholds in YAML configuration files.
  • Real training data: use photographs captured with the webcam rather than synthetic images.

System setup and hardware

  • Computer and OS: Windows 11 with Python 3.11 in the described setup.
  • GPU: NVIDIA RTX 5060 with 8 GB VRAM and CUDA enabled.
  • Software: PyTorch, Ultralytics YOLO, and OpenCV in a virtual environment.
  • Camera: standard USB or overhead webcam, with automatic reconnect as a goal.

Planned folder structure

  • config/ — settings such as config.yaml and data.yaml.
  • dataset/ and models/ — real training photos, labels, and trained weights such as best.pt.
  • src/camera.py and src/preprocessing.py — video capture and straightening angled camera views.
  • src/detector.py — detect game pieces and calculate their centers.
  • src/board_detector.py and src/coordinate_mapper.py — calibrate four board corners and map piece positions to the nine squares.
  • src/board_state.py — reduce flicker and maintain the digital board state.
  • src/capture_dataset.py and src/train.py — collect training photos and train the model.
  • src/main.py — run the complete application and open the two display windows.
  • tests/ — automated checks for coordinate mapping and anti-flicker logic.

Four-stage build plan

  1. Setup (Phases 1–3): check the GPU, create the project folders, and install packages.
  2. Train the AI (Phases 4–6): build camera capture, gather images across lighting conditions, label them, and train YOLO11n.
  3. Build the application (Phases 7–9): connect detection, add four-corner board calibration, map detections to squares, and implement anti-flicker logic.
  4. Launch and test (Phase 10): combine the live camera view and digital board, add q to quit and c to recalibrate, and run automated tests.

Handling real-world issues

  • Hands blocking a piece: wait for a stable detection across several frames (for example, 8 of 10) before updating the board.
  • Pieces near grid lines: use buffer zones to prevent a piece from rapidly switching between squares.
  • Duplicate detections: if more than one box appears in a square, keep the highest-confidence detection.
  • Pieces outside the board: ignore detections outside the calibrated corners.
  • Camera or model issues: attempt camera reconnection and handle unavailable model or GPU resources without crashing.

Quality checks

  • Mapping: test that pieces map to the correct squares and out-of-board pieces are ignored.
  • Stability: test that adding, moving, and removing pieces updates the digital board without flicker.
  • Live run: check video smoothness, corner calibration, and responsive display windows.

GitHub Pages: overview, advantages, and challenges

What is GitHub Pages?

GitHub Pages is a static website-hosting service that publishes websites from a GitHub repository. It can host websites made with HTML, CSS, and JavaScript, including portfolios, blogs, and project sites.

Why we switched from Google Sites

  • More design control: writing the site directly provides more flexibility than fixed templates.
  • Version control: GitHub tracks changes, making edits reviewable and previous versions recoverable.
  • Skill development: building and maintaining the site gives practical experience with web development.

Challenges during implementation

  • Code and file management: GitHub Pages requires managing project files and working with web technologies, unlike a drag-and-drop editor.
  • Setup and deployment: configuring the repository and understanding how publishing works took time.
  • Troubleshooting: deployment and code errors were not always immediately clear.

Data collection problem and takeaway

During VR headset and Nero arm data collection, the program was not adjusted to accommodate 40 recordings and stopped after 20. This left the dataset incomplete and meant the team had to investigate the error and consider repeating recordings.

Takeaway: review program settings—especially recording limits—before running a collection. Test the program with a small preliminary run to confirm it behaves as intended, reducing avoidable delays and improving the completeness of the dataset.
